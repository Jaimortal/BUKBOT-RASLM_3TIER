RASA STRUCTURED RETRIEVAL STABILIZATION PROMPT
Architecture: Rasa NLU + Query Normalization + Structured Retrieval + Context Memory + Clarification + Response Builder + Optional LLM Reranker

Use this prompt to continue building the chatbot phase by phase. Do not jump to the next phase until the current phase is implemented, debugged, and manually approved.

IMPORTANT RULES

1. Do not rewrite the whole chatbot at once.
2. Keep Rasa as the official NLU layer.
3. Keep JSON/database data as the source of truth.
4. Do not let an LLM generate official answers. If used later, it can only choose/rerank official JSON records.
5. Preserve the admin panel, map system, image upload, choices buttons, reports, audio response, and Knowledge Manager features.
6. Avoid redundant data when one structured record can handle the answer.
7. If a question is ambiguous, show clarification choices instead of guessing.
8. Test each phase before continuing.

DAY 2 - PHASE 2: QUERY NORMALIZATION HARDENING

Goal:
Improve messy user wording before retrieval.

Tasks:
1. Improve English typo normalization:
   - transfered -> transferred
   - offerd -> offered
   - admision -> admission
   - enrollmen -> enrollment
   - vallidate -> validate

2. Improve Bisaya normalization:
   - asa / aha -> where
   - unsaon -> how
   - pila -> how much
   - kanus-a / kanusa -> when
   - mobalhin / mamalhin / balhin / gapamalhin -> transferee
   - lantaw / makita -> view/check
   - resulta / resulta sa exam -> exam result

3. Improve acronym normalization:
   - COR
   - ID
   - COT
   - CAS
   - COB
   - COE
   - CON
   - CPAG
   - OSAS / OVPCASSS

4. Make normalization conservative:
   - Do not rewrite words when the meaning is uncertain.
   - Preserve original text for fallback/debug logs.

Expected output:
1. Updated query_normalizer.py or related normalization files.
2. Test results for typo, Bisaya, and acronym questions.

Before continuing to Day 3, the user must:

DAY 4 - PHASE 1: CONTEXT MEMORY SAFETY

Goal:
Make follow-up questions work without causing old-topic bugs.

Tasks:
1. Review context slots:
   - conversation_subject
   - conversation_subject_type
   - conversation_category
   - conversation_last_topic
   - conversation_last_intent
   - conversation_turns_remaining
   - any timestamp/TTL logic

2. Add safe context rules:
   - Use memory for follow-ups like "requirements?", "how much?", "how about COT?"

3. Use short TTL where needed:
   - common follow-ups: 3 to 5 minutes
   - sensitive service-specific follow-up: 5 minutes

DAY 6 - PHASE 1: OPTIONAL LLM RERANKER DRY RUN

Goal:
Use LLM only as a local optional reranker, not as the official answer generator.

Tasks:
1. Keep experimental_llm_layer separate.
2. Load candidates from official JSON records.
3. Let the LLM choose among top candidates only.
4. Do not allow the LLM to write a new official answer.
5. Return:
   - selected record ID
   - confidence
   - reason
   - official JSON answer

6. Add safe fallback:
   - if LLM is unavailable, use normal retrieval.
   - if confidence is low, ask clarification.

Expected output:
1. Dry-run script works.
2. No live bot integration yet.

Before continuing to Day 6 Phase 2, the user must:

DAY 6 - PHASE 2: OPTIONAL LLM INTEGRATION GATE

Goal:
Connect LLM reranker only if it improves accuracy safely.

Tasks:
1. Add feature flag:
   - LLM_RERANKER_ENABLED=false by default

2. Only call LLM when:
   - top scores are close
   - retrieval confidence is low/medium
   - question is long/messy
   - multiple candidates are plausible

3. Never call LLM when:
   - there is an exact location match
   - there is an exact display_name match
   - there is a precise child row match
   - the system already knows the answer confidently

4. Log LLM decisions for debugging.
5. Keep official response from JSON.

Expected output:
1. LLM can be turned on/off safely.
2. Bot still works without LLM.

Before finishing:
1. Run full smoke test.
2. Run ambiguity tests.
3. Run Bisaya/typo tests.
4. Run map and admin edit tests.
5. Confirm memory usage is acceptable.


FINAL ACCEPTANCE CHECKLIST

The architecture is considered stable only when:

1. Rasa train succeeds.
2. Rasa action server has no slot/action errors.
3. Express server does not crash.
4. Frontend builds successfully.
5. Admin can edit knowledge data safely.
6. Maps show pins and routes after admin edits.
7. Choices do not cause loops.
8. Follow-up memory works and expires safely.
9. Typos and common Bisaya forms improve retrieval.
10. Wrong-answer cases are logged and fixed through data or scoring.
11. LLM, if enabled, only reranks official records.
